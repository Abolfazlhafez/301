# کارگاه‌یار (Karegah-Yar)

اپلیکیشن مدیریت کارگاه ساختمانی، آفلاین-محور، ساخته‌شده با React + TypeScript + MUI v5 +
Dexie/IndexedDB و Capacitor (اندروید).

## پیش‌نیازها

- Node.js نسخه ۲۰ یا بالاتر
- npm

## اجرای محلی

```bash
npm ci
npm run dev          # اجرای نسخهٔ توسعه در مرورگر
npm run build         # بررسی TypeScript + بیلد نهایی وب در dist/
npm run lint           # بررسی Lint (oxlint)
```

## معماری ذخیره‌سازی (از نسخهٔ 1.2.0) — بدون IndexedDB/WebView

برای کاهش وابستگی به Android System WebView (و کرش‌های مرتبط با IndexedDB و Blobهای حجیم)،
ذخیره‌سازی از Dexie/IndexedDB به لایهٔ نیتیو منتقل شد:

| چه چیزی | کجا ذخیره می‌شود |
| --- | --- |
| رکوردها (کارگر، حضور، صندوق، طبقه، ...) | **SQLite نیتیو** (`@capacitor-community/sqlite`) |
| عکس‌ها و یادداشت‌های صوتی | **فایل واقعی** در `Directory.Data/blobs/` (Capacitor Filesystem)؛ در دیتابیس فقط مسیرشان |
| پیش‌نویس فرم‌ها، جستجوهای اخیر | `@capacitor/preferences` (SharedPreferences نیتیو) — مثل قبل |
| تم، زبان، واحد پول | هنوز `localStorage` (سه کلید کوچک؛ فهرست کارهای باقی‌مانده را ببینید) |

نکته‌های فنی:

- `src/core/db.ts` همان API قبلی (`db.workers.get/put/where(...)...`، `db.transaction`) را نگه می‌دارد؛ زیرش
  `src/core/storage/nativeStore.ts` است: کش در حافظه + نوشتن هم‌زمان (write-through) در SQLite.
  هر تغییر قبل از resolve شدن Promise در SQLite ماندگار می‌شود؛ تراکنش‌ها یک batch اتمیک‌اند و در خطا rollback می‌شوند.
- خواندن رکورد عکس/صوت دیگر `blob` برنمی‌گرداند؛ `blobUrl` / `displayBlobUrl` می‌دهد (مستقیم برای `<img>`/`<audio>`).
  برای Blob واقعی (اشتراک‌گذاری، بکاپ، تبدیل HEIC): `db.readBlob("photos", id, "blob")`.
- مهاجرت نصب‌های قدیمی **خودکار و یک‌باره** است (`storage/migrateFromIndexedDb.ts`): کپی ← اعتبارسنجی
  (شمارش رکورد + وجود/اندازهٔ هر فایل) ← فقط در صورت موفقیت، حذف IndexedDB قدیمی. در صورت خطا،
  دادهٔ قدیمی دست‌نخورده می‌ماند و دفعهٔ بعد دوباره تلاش می‌شود. schema قدیمی Dexie فقط در `legacyDb.ts` نگه داشته شده.
- اگر رندرر WebView بمیرد، `MainActivity` آن را «هندل‌شده» اعلام می‌کند (به‌جای کرش اپ) و Activity را بازسازی می‌کند
  (با حد ۳ بار در ۱۵ ثانیه برای جلوگیری از حلقه).
- در مرورگر (`npm run dev`) SQLite نیتیو نیست؛ fallback روی IndexedDB خام است. در تست‌های Node حافظه است.
- تست‌ها: `npm run test:native-storage` (موتور، تراکنش، فایل‌ها، مهاجرت با عکس واقعی) و `npm run test:experimental`.

⚠️ قبل از انتشار برای کاربران واقعی: روی یک گوشی واقعی با **داده و عکس واقعی** نصبِ روی نسخهٔ قدیمی (Update، نه نصب تازه)
را تست کنید. بکاپ بگیرید. تست روی دستگاه از داخل محیط توسعهٔ این تغییرات ممکن نبود.

## بکاپ ابری اختیاری (Supabase) — از نسخهٔ 1.5.0 تکه‌ای

بکاپ ابری یک آینهٔ رمزنگاری‌شدهٔ بکاپ محلی در پروژهٔ Supabase شخصی خود شماست. از 1.5.0 بکاپ در تکه‌های ≈۵۰۰KB
زیر یک `upload_id` تازه آپلود می‌شود و فقط بعد از آپلود کامل، ردیف `karegah_yar_backup_heads` به آن اشاره می‌کند؛
پس آپلود قطع‌شده هرگز بکاپ سالم قبلی را خراب نمی‌کند. SQL ساخت جدول‌ها را در «تنظیمات ← بکاپ ابری ← راهنمای ساخت
جدول» ببینید (اجرای دوباره بی‌خطر است). اگر آن را اجرا نکنید، بکاپ مثل نسخه‌های قبل در جدول قدیمی
`karegah_yar_device_backups` (یک ردیف) ذخیره می‌شود و بازیابی از ردیف‌های قدیمی هم همچنان کار می‌کند.
⚠️ منطق این بخش فقط با Supabase ساختگی تست شده؛ روی پروژهٔ واقعی خودتان یک بکاپ و بازیابی امتحان کنید.

## شروع سریع — Push به گیت‌هاب و ساخت APK

این پروژه یک Workflow آماده در `.github/workflows/build-apk.yml` دارد که با هر Push به
شاخهٔ `main`، به‌صورت خودکار پروژه را بیلد کرده و یک APK امضاشده می‌سازد.

### با GitHub Desktop (روش پیشنهادی)

1. پوشهٔ استخراج‌شدهٔ این پروژه را در GitHub Desktop باز کنید:
   `File → Add Local Repository…` و مسیر این پوشه را انتخاب کنید.
2. **اگر مخزن گیت‌هاب هنوز ساخته نشده:** دکمهٔ **Publish repository** را بزنید.
   حتماً گزینهٔ **Keep this code private** را فعال نگه دارید (دلیلش در بخش
   «نکتهٔ امنیتی» پایین همین فایل توضیح داده شده).
3. **اگر مخزن از قبل وجود دارد:** تغییرات به‌صورت خودکار در تب Changes دیده می‌شوند؛
   یک توضیح کوتاه در قسمت Summary بنویسید و **Commit to main** را بزنید، سپس
   **Push origin** را بزنید.
4. به مخزن پروژه در وب‌سایت گیت‌هاب بروید → تب **Actions** → اجرای در حال انجام
   («Build Android APK») را ببینید. حدود ۵ تا ۱۰ دقیقه طول می‌کشد.
5. وقتی اجرا با علامت سبز تمام شد، روی همان اجرا کلیک کنید؛ در پایین صفحه بخش
   **Artifacts** یک فایل به نام `karegah-yar-apk` است — آن را دانلود کنید
   (یک فایل zip است)، از حالت فشرده خارج کنید تا فایل `.apk` واقعی به دست بیاید،
   و آن را به گوشی اندروید منتقل و نصب کنید.

### با خط فرمان Git

```bash
git init
git add .
git commit -m "به‌روزرسانی پروژه"
git branch -M main
git remote add origin <آدرس-مخزن-گیت‌هاب-شما>
git push -u origin main
```

(اگر مخزن از قبل وصل است، مراحل `init`/`remote add` را رد کنید و فقط
`git add . && git commit -m "..." && git push` کافی است.)

## نکتهٔ مهم — versionCode قبل از هر Push جدید

فایل `android/app/build.gradle` مقدار `versionCode` را دارد. اندروید نصب یک نسخهٔ
جدید را روی نسخهٔ نصب‌شدهٔ قبلی فقط زمانی Update حساب می‌کند که این عدد از قبلی
**بزرگ‌تر** باشد. پیش از هر Push که قرار است روی نصب فعلی گوشی‌ها Update بخورد،
این عدد را دست‌کم یک واحد افزایش دهید (`versionName` صرفاً نمایشی است و لازم
نیست حتماً تغییر کند).

## نکتهٔ امنیتی — کیستور امضای Release

فایل `android/app/karegah-yar-release.keystore` و رمز آن (در
`android/app/build.gradle`) عمداً همراه پروژه Commit می‌شوند تا همهٔ نسخه‌های
Release با یک کلید یکسان امضا شوند (در غیر این صورت، هر Push نصب Update را
روی نسخهٔ قبلی رد می‌کرد). **پیامد این تصمیم:** هرکسی که به این مخزن گیت‌هاب
دسترسی بخواند داشته باشد، هم کیستور و هم رمز آن را می‌بیند. به همین دلیل:

- مخزن را حتماً **Private** نگه دارید.
- اگر روزی خواستید این مخزن را Public کنید یا با کسی دیگر Share کنید، بهتر
  است پیش از آن، کیستور و رمزش را از کد خارج کرده و به‌جای آن از
  GitHub Actions Secrets استفاده کنید — در صورت نیاز می‌توانم این تغییر را
  هم برایتان انجام بدهم.
